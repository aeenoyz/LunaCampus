🛡 방어 노트 · 왜 뚫렸나

화면에서 숨기는 것은 보안이 아닙니다. display:none, hidden은 사용자에게 안 보이게 할 뿐, 데이터는 이미 브라우저까지 전송된 상태입니다.

어떻게 막나: 권한 없는 사용자에게는 서버가 그 HTML 자체를 내려보내지 않아야 합니다. 버튼을 숨기는 게 아니라, 버튼이 없는 페이지를 보내는 것입니다.

🛡 방어 노트 · 왜 뚫렸나

입력을 문자열로 이어붙여 쿼리를 만들면(SQL 인젝션), 사용자가 따옴표 하나로 문장 구조 자체를 부술 수 있습니다. ' OR '1'='1 은 "비밀번호가 X 이거나, 아니면 1=1(항상 참)"이 되어 조건이 무력화됩니다.

어떻게 막나: 입력을 문장에 섞지 말고 매개변수(Prepared Statement)로 분리합니다. WHERE pw = ? 처럼 자리표시자를 두면, 사용자가 무엇을 넣든 "값"으로만 취급되고 문장 구조는 절대 바뀌지 않습니다. 이게 SQL 인젝션의 근본 해결책입니다.

참고 · <script>가 아니라 따옴표가 무기라는 점에 주목. 공격의 재료는 늘 "그 문맥에서 특별한 의미를 가진 문자"입니다.

🛡 방어 노트 · 왜 뚫렸나

사용자 입력을 HTML로 해석해서 그리면(XSS), 글 대신 코드를 심을 수 있습니다. 저장형 XSS는 그 글을 본 다른 사람의 브라우저에서도 실행되기 때문에, 쿠키 탈취·계정 도용·가짜 화면 삽입으로 번집니다.

어떻게 막나: 입력을 화면에 넣을 때 이스케이프합니다. < 를 &lt; 로 바꿔 "글자로만" 보이게 하는 것이죠. 코드에서는 innerHTML 대신 textContent 를 쓰고, 꼭 HTML을 허용해야 하면 DOMPurify 같은 검증기를 거칩니다.

참고 · <script>태그를 넣으면 왜 실행이 안 됐을까요? innerHTML로 삽입된 script는 브라우저가 실행하지 않기 때문입니다. 그래서 실제 공격은 onerror 같은 이벤트 핸들러를 씁니다. 방어는 "태그 하나 막기"가 아니라 "입력을 코드로 해석하지 않기"여야 하는 이유입니다.

🛡 방어 노트 · 왜 뚫렸나

주소·번호만 바꿔 남의 데이터를 보는 취약점(IDOR)입니다. 서버가 "요청에 적힌 학번"의 데이터를 그냥 내주고, "요청한 사람이 그 학번의 주인이 맞는지"를 확인하지 않았습니다. 실제로 대형 서비스에서 URL 숫자 하나로 수백만 명 개인정보가 새는 사고가 반복됩니다.

어떻게 막나: 모든 데이터 조회에서 서버가 "로그인한 사람 = 데이터 주인"인지 대조해야 합니다. 요청에 적힌 번호를 믿지 말고, 세션에 저장된 본인 식별자를 기준으로 조회하는 것이 원칙입니다.

참고 · 방금 조회는 진짜 네트워크 요청이었습니다(Network 탭에서 확인). 실제 서비스의 IDOR도 정확히 이렇게 생겼습니다 — 클라이언트가 id로 조회하고, 서버가 소유권을 확인하지 않는 것.

🛡 방어 노트 · 왜 뚫렸나

프론트엔드에 비밀은 존재할 수 없습니다. HTML·JS·주석·소스맵까지 전부 사용자 컴퓨터로 내려갑니다. 난독화를 해도 실행되는 이상 복원됩니다. 깃허브에 올라간 키가 자동 수집 봇에 털려 요금 폭탄을 맞는 사고가 매년 반복됩니다.

어떻게 막나: 키는 서버 환경변수에 두고, 외부 API 호출은 서버가 대신(프록시)합니다. 이미 노출된 키는 지우는 걸로 끝나지 않고 즉시 폐기하고 새로 발급해야 합니다 — 커밋 기록에 영원히 남기 때문입니다.
